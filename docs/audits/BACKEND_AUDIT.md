## Two-column reading order: root cause, first fix, and the real fix

**User report**: "I think the pipeline broke when it comes to double column pages." Confirmed real: a front-matter page pairing "Terms of Reference" (left column) with "Acknowledgements", a contributor list (right column), read as one interleaved sequence in the exported HTML.

**First fix (superseded)**: traced the bug to `toc_hierarchy.py`'s `apply_outline`, which merges restored/promoted headings into body content via a blanket `positioned.sort(key=(page, top, priority))` — discarding whatever order the content arrived in. Patched this with `_column_offsets_by_page`, a geometric column-clustering heuristic (left-edge clustering, a 35%-page-width threshold, a "each column needs ≥2 blocks" count check) that added a per-block vertical offset so the sort would read one column fully before the next. Verified against real documents, fixed 47→16 flagged pages across all 15 documents, applied retroactively to persisted `blocks.json` for every document without re-running Docling (a live run is required for real confidence data and Docling is confirmed non-deterministic elsewhere in this file — re-extracting would have silently discarded manual corrections already applied this session).

**Asked to research a non-heuristic fix.** Traced Docling's own raw reading order directly (before any of this codebase's post-processing) for two different still-broken pages — the Bail Act's Terms of Reference page and an ART&Adoption bibliography page with a stray off-page bounding box (`left: -528.3`) that was defeating the column-clustering heuristic. **In both cases, Docling's own order was already completely correct** — left column in full, then right column in full, zero interleaving. Confirmed `docling_ibm_models` ships a genuine graph-based reading-order algorithm (`reading_order/reading_order_rb.py`, r-tree spatial index, up/down/left/right adjacency mapping) — not naive top-to-bottom extraction. Checked this codebase's own intermediate block order (the input to `apply_outline`, not just raw Docling) for the same bibliography page and confirmed it was *also* already clean going in.

**Conclusion**: the bug was never "the codebase's column detection isn't good enough" — it was "the codebase re-derives order it already had, correctly, and then discards it." Checked every other position-based sort in `pipeline.py`, `toc_hierarchy.py`, and `visual_structure.py` for the same mistake — none of the others have it; they serve genuinely different jobs (building spatial regions from raw PDF vector graphics, ordering printed-TOC entries) where there's no pre-existing good order to protect.

**Real fix**: rewrote `apply_outline` to never re-sort real content at all. Each page's existing block order (already correct) is now preserved completely; only outline entries (headings Docling missed or mislabeled — a small minority of blocks) get spliced into their approximate position within that page's own sequence via a local insertion-index scan, rather than a global re-sort. Deleted `_column_offsets_by_page` and `_COLUMN_OFFSET_STEP` entirely — the geometric heuristic is no longer needed for anything.

**Verified against real documents, compared directly against the old heuristic fix**:

- Funeral and Burial Instructions, Neighbourhood Tree Disputes, Proceedings page 2 (front-matter imprint template): now clean.

4 new regression tests in `test_toc_hierarchy_columns.py`, rewritten to test `apply_outline` directly (constructing a bare `TocHierarchyResolver` via `object.__new__` plus a minimal `TocOutline`, avoiding the PDF/document dependencies `__init__` needs) rather than the deleted helper function. Full backend suite: 213/213 pass.

**Full-corpus verification, old heuristic vs. new order-preserving fix, compared directly**: 16 → 6 flagged pages across all 15 documents, zero regressions anywhere. The 6 remaining are two genuinely different, smaller problems the redesign incidentally surfaced (previously masked by the old blanket re-sort "accidentally" correcting them): a print-shop InDesign export debug line (`"...indd 17"`) that *Docling's own* reading-order model occasionally misplaces relative to a chapter-opening sidebar (3 pages, ART&Adoption) — not a column-detection failure, since Docling gets the actual columns right on the same pages; and one page (Committals p2) with a stray indicia line plus two repositioned images. ## User-reported bug, confirmed via screenshots: footnote content leaking into visible body text

User attached two screenshots of "Funeral and Burial Instructions" paragraph 2.5: footnote markers 5 and 6 rendered correctly as blue superscript links, but marker 7 rendered as plain trailing text, and — directly below the paragraph — a lone "2" and "Leeburn v Derndorfer (2004) 14 VR 100, 104" appeared as their own visible body paragraphs, exactly where a footnotes section should have been instead.

**Root cause, confirmed against `blocks.json`**: footnote 2's number and citation text were split into two separate Docling text items — a block containing only "2" and a block containing only the citation — both labelled `"text"` instead of `"footnote"`, sitting between correctly-labelled footnotes 1 and 3. Neither block ever reached the footnotes list; both rendered as ordinary body paragraphs.

**Scope, found by building a classifier before writing any fix** (a bare-number `"text"` block only counts if its number directly continues the real footnote sequence — ruling out unrelated bare numbers elsewhere in the document): **645 confirmed instances across 8 of the 15 documents**. The pattern turned out more general than the single reported case: some documents split not just one marker but a *run* of several consecutive markers (e.g. "156", "157", "158", "159", "160") before a matching run of citation blocks resumed — verified directly in "Neighbourhood Tree Disputes" that the two runs pair up positionally in order (156 with the first content block, 160 with the last), with normal numbered footnotes resuming cleanly afterward.

**Fix**: `pipeline.py` gained `_repair_split_footnote_markers`, run as the first post-processing step after block extraction (before `_relabel_footnote_lists`). It detects a maximal run of consecutive marker-only blocks continuing the real footnote sequence, then requires *exactly* that many content-shaped blocks immediately following with nothing else in between — anything that doesn't resolve this cleanly (marker/content count mismatch, an interruption) is left untouched rather than guessed at.

**Two real bugs caught by testing against the actual edge cases, not just the happy path**: (1) a candidate "content" block that was actually a complete, already-correctly-numbered footnote (e.g. "4 Another genuine citation") was being wrongly consumed as content for merging — caught by a test asserting mismatched counts should be left alone, which initially failed for the wrong reason. Fixed by excluding any `"footnote"`-labelled candidate that already has its own leading number. (2) An earlier version excluded any content candidate merely for starting with *any* number, which would have wrongly rejected genuine content like "24 hours notice was required..." — added a dedicated test for this exact shape.

5 new regression tests reproducing the real single-split and five-in-a-row shapes verbatim, plus the two edge cases above. Full backend suite: 223 pass (218 + 5).

**Verified against the real reported document before and after**: reprocessed "Funeral and Burial Instructions" from its cached `docling.json` — footnote 2 now reads "2 Leeburn v Derndorfer (2004) 14 VR 100, 104", correctly labelled and in clean sequence with 1, 3, 4, 5. One case had the citation text itself mislabelled `"footer"` rather than `"text"`/`"footnote"`. Extending the fix to skip over header/footer blocks would risk swallowing genuine footer noise as footnote content — left as a known, honestly-characterised gap rather than a rushed extension.

## User-reported bug, confirmed via screenshots against the real source PDF: recommendation numbers showing as bullets, then jumping backwards

User attached a screenshot of "Funeral and Burial Instructions" → Recommendations, plus (in a follow-up) a screenshot of the actual source PDF page for the same section as ground truth: "1", "2", "3"... top-level recommendation numbers, each with lettered `(a)(b)` and roman `(i)(ii)` sub-clauses properly nested underneath. The live render instead showed `• 1 Victoria should introduce an Act that:` — a bullet, with the number stuck in the visible text — and, further down the same list, explicit numbers that visibly jumped backwards (a screenshot showed "18." "19." "20." where the source read "18." then a lettered sub-clause).

**Root cause, confirmed against `blocks.json` and the real source layout**: Docling extracts an entire numbered-recommendation list as one completely flat group — every item at `level: 0`, with no nesting information distinguishing a top-level recommendation from its own lettered/roman sub-clauses. Two different shapes of this same underlying flatness turned up in the same document:

1. **Bare, unmarked top-level numbers** (`#/groups/7`, recs 1-4): each item's own text starts with the number and nothing else — `"1 Victoria should introduce an Act that:"` — with no marker field set at all, same as its `"(a) allows..."` sub-clauses. `exporter.py`'s existing `promote_bare_number_markers` (added earlier this session for a different, *pure* bare-number-list case) requires *every* entry in the list to match before promoting any of them — a single `"(a)"` anywhere disqualified the whole list, so the genuine top-level numbers fell through to plain unordered bullets with the digit left sitting in the visible text.
2. **Already-marked top-level numbers** (`#/tables/6`, recs 12-18): here Docling *does* give the top-level number its own marker (`"12."`, `"13."`) and the sub-clauses their own marker too (`"(a)"`, `"(b)"`) — but still all at the same flat level, so they all merge into one shared `<ol>`. Three unvalued sub-items after `"13."` auto-continue the browser's counter to 16; the next explicit `value="14"` on the real next recommendation then snaps the visible number backwards from 16 to 14 — exactly the jump the user's screenshot caught.

**Fix**: added `_interleaved_recommendation_numbers` to `exporter.py`, run inside `_list_publication_blocks` before the main per-entry loop. It detects either shape — a bare leading number with no marker, or an already-marked plain decimal marker (`"12."`, `"(12)"`; a decimal *paragraph* marker like `"2.6"` never matches, so that separate, already-working code path is untouched) — and treats a match as a genuine top-level recommendation number only when (a) the matched numbers run strictly consecutively (1, 2, 3, ... — the same structural safeguard `promote_bare_number_markers` already used, ruling out coincidental runs like ascending statistics) and (b) at least one *other*, non-candidate entry sits between two of them (true interleaving — a plain, adjacent `"7."` immediately followed by `"8."` is a normal two-item ordered list, not this shape, and is deliberately left alone). Each matched recommendation number is then rendered standalone via the existing `reader-numbered-paragraph` treatment already used elsewhere for decimal paragraph numbers (`"2.39 ..."`), instead of being forced into a list counter it was never really part of. `promote_bare_number_markers` itself was left exactly as it was (still handles the *pure*, non-interleaved bare-number-list case it was built for) — the two functions are mutually exclusive by construction, since an entry `promote_bare_number_markers` already promoted to a real marker no longer matches the "unmarked" half of the new detector, and a pure run with no interleaving is explicitly excluded from the new detector's output.

**Scope, checked empirically against the whole corpus**: reprocessed all 15 real documents through `build_publication` — **7 documents produced standalone numbered-recommendation paragraphs**: Review of the Bail Act (114), Funeral and Burial Instructions ×2 (18, 25), Committals (30), Birth Registration and Birth Certificates (8), Inclusive Juries (12), Neighbourhood Tree Disputes (59), Contempt of Court (125), Proceedings (27). Spot-checked every genuine consecutive run within every section for gaps or false positives (grouping only within contiguous stretches, since separate list blocks elsewhere in the same document legitimately restart their own numbering) — every run detected is strictly consecutive with zero gaps, zero false positives, across the entire corpus.

Added 2 new regression tests reproducing both real shapes verbatim — the bare-unmarked case (`#/groups/7`'s exact text) and the already-marked case (`#/tables/6`'s exact markers and the specific 16→14 backward-jump this fix prevents). Confirmed via `git stash`/`git stash pop` on `exporter.py` that both fail without the fix, for the right reason (zero numbered paragraphs produced instead of the expected sequence). ## Follow-up, requested by the user: restore the lettered/roman sub-clause nesting flagged above

The previous fix restored each top-level recommendation number to its own correct display, but left its lettered `(a)(b)` and roman `(i)(ii)` sub-clauses flattened into one auto-numbered decimal list (`1. 2. 3. 4.`) — the user supplied a screenshot of the actual source PDF as ground truth, showing genuine two-level nesting (`1 -> (a)(b) -> (i)(ii)`), and asked for that to be fixed too.

**The core problem**: Docling extracts these lists completely flat — every sub-clause at `level: 0`, with zero indentation data distinguishing a lettered item from its own roman sub-items. The marker's own shape, and its sequence relative to markers already seen, is the only signal left to reconstruct the source's real outline depth.

**Fix**: added `_next_nesting_level` to `exporter.py`, a stack-based inference that processes each group's markers in order and tracks one frame per currently-open depth (its kind — decimal/alpha/roman — and last value). A marker that continues the current top frame's sequence (value + 1, same kind) stays at that depth; one that continues an *ancestor* frame's sequence pops back up to it (e.g. `"(b)"` resuming after a nested `"(i)(ii)"` run under `"(a)"` — the "23. ... (a) ... (i) ... (ii) ... (b)"` shape found in the real corpus); one that starts fresh at value 1 opens a new, deeper frame as a child of whatever was current. Feeding it is `_marker_candidates`, which reads a marker's shape into every *valid* interpretation rather than picking one upfront — a bare `"(i)"` is genuinely ambiguous (the letter after "h", or roman numeral 1) until the surrounding sequence disambiguates it — backed by a canonical roman-numeral parser (`_roman_to_int`, round-trip validated against `_int_to_roman` so malformed sequences like `"iiii"` or `"vx"` are rejected rather than misread).

Wired into `_list_publication_blocks`: a `nesting_stack`, reset on every `flush()` so one recommendation's sub-clauses never inherit the previous one's outline state, feeds `_next_nesting_level` whenever an item is ordered and Docling's own `level` was 0 (meaning it carries no real hierarchy to begin with — anywhere Docling *does* provide genuine nesting data, that's trusted unchanged, untouched by this inference). Each inferred level also carries a `kind` and, for alpha/roman items that had no explicit value before, a real sequence value (1, 2, 3 for `(a)(b)(c)`) — so a genuine gap in the source is preserved instead of silently relying on the browser's auto-increment, the same principle already applied to decimal markers and footnote numbers throughout this session.

On the rendering side, `preview_html.py`'s `_render_list_items` picks a CSS class (`reader-source-list--alpha` / `--roman`) from the group's own inferred kind, backed by two new rules (`list-style-type: lower-alpha` / `lower-roman`) alongside the existing decimal default — combined with the `value` attribute already being set, the browser's own numbering-format conversion does the rest (`value="2"` under `lower-alpha` displays as "b.", not "2."), with no other rendering-path changes needed. `_nested_list_tree` already supported real multi-level nesting from `level` values; it simply had nothing but zeros to work with before this fix.

**Verified against the real document, matching the user's own source-PDF screenshot exactly**: recommendation 1's `(a)(b)` render as their own alpha-styled list, with `(i)(ii)` correctly nested *inside* `(b)`'s own `<li>` as a roman-styled sub-list. ## Pre-production sweep: security, false positives across every label (not just footnotes), and cross-stack error handling

User asked for a full, ship-it audit of the whole system — explicitly not limited to footnotes: "the system must not produce false positives at all... not just footnotes all the labels as well." What follows are the confirmed, fixed issues.

### CRITICAL/HIGH — Access control: 10 endpoints serving in-progress document content had no auth check at all

`main.py` had a real, exploitable gap: `get_document`, `processing_summary`, `processing-state`/`status`, `get_review_items`, `get_metadata`, `publication`, `review_evidence`, `metadata_evidence`, and the raw `exports/docling.json` download all took no `user` parameter and called no ownership check — while the *list* endpoint (`/api/documents`) already correctly scoped results to the caller, every one of these *detail* endpoints for the same documents was fully public to anyone who had (or guessed, or had leaked to them) a document id. `source_pdf` (the original uploaded PDF) was in the same boat, but is a special case: the *approved* export embeds it as a public "view original source" citation link with no Supabase session, so it can't simply require auth unconditionally.

**Fix**: added `user: CurrentUser` + `_require_owner(record, user)` to all ten, matching the exact pattern already used by `delete_document`/`start_processing`. For `source_pdf`, added a new `get_current_user_optional` dependency (`auth.py`) that returns `None` instead of 401 when no bearer token is presented — the endpoint now requires ownership before approval, and is genuinely public only once `approved_at` is set. Verified this required no frontend changes: `httpClient.ts`'s `apiRequest` already attaches the Supabase bearer token to *every* authenticated request unconditionally, so these endpoints were only ever reachable without a token by a request that deliberately omitted one.

Added `test_unapproved_document_read_endpoints_are_scoped_to_their_uploader` and `test_source_pdf_requires_auth_before_approval_but_is_public_once_approved` to `test_security.py`. Confirmed both fail without the fix (200 instead of 404/401) via `git stash`. Full backend suite: 232 pass.

### CRITICAL — Watermark exclusion could delete a real paragraph that merely used the same word once

`annotate_pdf_artifacts` (`visual_structure.py`) matched a Docling text item against a detected watermark span via plain substring containment (`candidate["text"] in text`) plus only a 45%-bbox-overlap check. Reproduced directly: a page with a "DRAFT" watermark (fontsize 120) and an unrelated paragraph reading "...reviews the **draft** recommendations submitted by stakeholders..." — the paragraph's own bounding box sits inside the watermark's large bounding box, and its full text contains the watermark's short span as a substring, so the *entire real paragraph* got silently excluded from the accessible output. A second, related bug in the same function: any text seen 3+ times *on one page* (≤60 chars) was flagged as a "repeated decorative fragment," with no positional requirement at all — a checklist's "Not applicable" appearing three times in one table would be deleted as if it were a running footer.

**Fix**: the substring-containment match now requires the matched watermark span to cover at least 60% of the item's own text length when the direction is short-inside-long (an item that essentially *is* the watermark, not a paragraph that happens to mention it once); the reverse direction (item fully inside a longer span, from Docling occasionally fragmenting one watermark into several small items) was left as-is, since that direction can't produce this false positive. The repeated-fragment rule was rebuilt on the same three conditions `toc_hierarchy.py`'s own, already-correct running-header detector uses: the text must sit near the very top or bottom page margin, recur on **3+ distinct pages** (not same-page count), within a dense page range, at a **consistent vertical position** across those pages — a real running header/footer/watermark, not a coincidental short phrase reused a few times.

Corpus-wide before/after (all 11 real documents, from cached `docling.json` + `source.pdf`): the position-blind, cross-page version I initially wrote was actually *worse* than the original bug (repeated-fragment counts exploded 10x, since dropping the same-page requirement without adding a position requirement made it fire on any short phrase reused anywhere in a 200-page document) — caught this by comparing before/after corpus numbers rather than trusting the unit tests alone, and redesigned around the position-consistency guard before shipping it. Final numbers land close to or modestly above the original buggy counts (genuine running headers the old same-page-only rule was *missing* are now correctly caught — spot-checked a sample: all real chapter-title headers and page numbers, zero false positives found).

4 new regression tests in `test_visual_structure.py`, including the exact watermark-plus-paragraph reproduction, the same-page checklist case, and the positive case (a genuine 4-page running header is still excluded). Confirmed via `git stash` that both false-positive tests fail without the fix. Full backend suite: 235 pass.

### HIGH — A standalone "Recommendations" chapter was always demoted to H2

`_normalise_outline_levels` (`toc_hierarchy.py`) unconditionally demoted any TOC entry starting with "Recommendations" to level 2, with no indentation check at all — unlike every other subsection demotion, which only fires when an entry is genuinely indented deeper than the current chapter. In a legal/government report, "Recommendations" is extremely commonly its own dedicated top-level chapter — often the single most important one — and this rule would silently nest its entire content under whatever chapter happened to precede it in the navigation, every time, regardless of how it was actually printed.

**Fix**: removed the special-cased, indentation-blind branch entirely. "Recommendations" now goes through the exact same indentation test every other subsection title is judged by — demoted only when genuinely indented deeper than its chapter, kept at top level when printed at the same indent as its sibling chapters. (Deliberately *not* added to `_ALWAYS_TOP_LEVEL` alongside glossary/bibliography/index — those are always standalone; "Recommendations" genuinely appears both ways in this corpus, so the indentation signal has to keep doing the real work.)

2 new tests in `test_heading_resolver.py` — a standalone Recommendations chapter at top-level indent (must stay H1) and an indented Recommendations sub-heading under a chapter (must still demote to H2, preserving the original rule's legitimate purpose). Confirmed the first fails without the fix via `git stash`. Full backend suite: 237 pass.

### CRITICAL — A WordPress publish race could create a real page with zero record of it anywhere

`publish_to_wordpress` (`main.py`) called `wordpress.publish()` — which creates a real WordPress page — *then* checked whether the document's approval had changed while that call was in flight, raising a 409 *before* writing either the local cache or the durable Supabase registry if it had. Anyone editing/re-approving the document (or another admin revoking approval) while a colleague's publish request was mid-flight would leave a real WordPress page durably unrecorded on the Konverter side — silently defeating the very duplicate-publish protection the previous commit (86bf9d8) had just added, since the next publish attempt's registry lookup would see nothing and publish straight through again.

A second bug in the same feature: `wordpress_registry.find_latest` treated *any* failure — a genuine "no prior publish" result, a network timeout, a 5xx from Supabase, malformed JSON — identically, returning `None` in every case. A transient Supabase hiccup would silently disable the duplicate-publish safeguard with nothing but a server-side `log.warning` — invisible to the user, who'd get a normal-looking successful publish that might now be an undetected duplicate.

**Fix**: reordered `publish_to_wordpress` so the artifact write and durable-registry write happen unconditionally right after a successful `wordpress.publish()` call, before the staleness check — the check is now purely informational (a 409 that still confirms "page N was published, but review the document"), never a reason to skip persistence. `wordpress_registry.py` gained `RegistryUnavailableError`, raised only on an actual lookup failure (not on the deliberately-supported "Supabase not configured" no-op mode, which an existing test explicitly documents as intended behaviour and had to be preserved) — `main.py` now fails the publish request closed (503) on this exception rather than silently proceeding to publish blind.

2 new tests in `test_wordpress.py`: one simulates the exact race (a fake publisher mutates `approved_at` mid-call) and confirms the page is durably recorded despite the resulting 409; the other confirms a broken registry blocks the publish (503) instead of skipping the duplicate check. Both confirmed to fail without the fix via `git stash`. Full backend suite: 239 pass.

### HIGH — OpenAI network/timeout errors escaped the chat and TTS streams uncaught

`stream_chat_completion` and `synthesize_speech` (`chat.py`) only handled OpenAI's own HTTP error *responses* (status >= 400) — a connect timeout, DNS failure, or read timeout is a transport-level `httpx` exception, never reaches that check, and wasn't caught anywhere. Both call sites in `main.py` only catch `(OpenAINotConfiguredError, OpenAIRequestError)`; an uncaught `httpx.ConnectTimeout` would escape the async generator raw, inside a `StreamingResponse` whose 200 status was already sent — an abrupt connection drop instead of the graceful, logged failure every other OpenAI error path gets.

**Fix**: wrapped both functions' request bodies in `try/except httpx.HTTPError`, converting any transport-level failure into `OpenAIRequestError` — the same exception type every caller already handles correctly. Also fixed the TTS handler's `except (...): return` in `main.py`, a genuine empty error handler with zero logging (unlike its two chat siblings) — TTS failures were completely invisible server-side.

2 new tests in `test_chat.py`, directly exercising `stream_chat_completion`/`synthesize_speech` against an `httpx.MockTransport` that raises `ConnectTimeout`. Confirmed both raise the raw, uncaught `httpx.ConnectTimeout` without the fix. Full backend suite: 241 pass.

### HIGH (frontend) — "Upload picture" claimed success without uploading anything

In an accessibility pipeline, this is exactly the dangerous class of bug the user flagged: a reviewer would see a missing-picture item marked resolved and move on, while the shipped document still has no picture — a false-positive resolution with no signal anything is wrong.

**Fix**: rather than build a new, unscoped, untested image-upload backend feature under time pressure, removed the fake control entirely — replaced with an honest message directing the reviewer to reject the item, which already works correctly via the standard Accept/Remove actions. No test previously covered this (confirmed via grep), so nothing needed updating for the removal.

### HIGH (frontend) — Saving an edit had no double-submit guard and no error handling

Every other reviewer action (`act`, `restoreToOutput`) guards against double-clicking via an `actingItemId` re-entrancy check and disables its button while in flight; `saveEdit` had neither, and — unlike its siblings, which at least have a `finally` — had no error handling *at all*. **Fix**: brought `saveEdit` in line with the established `act`/`restoreToOutput` pattern (re-entrancy guard, disabled button, `try/catch/finally` with an error toast on failure) — and added the same `catch` to `act`/`restoreToOutput` themselves, which had the guard and `finally` but no actual error handling either.

2 new tests in `ReviewPage.test.tsx` (added a `ToastProbe` helper reading `toastState` from context, since the actual toast UI isn't part of this page's own render tree): a failed save shows an error toast and keeps the edit open with the in-progress change intact, and double-clicking "Save changes" only fires one request. Confirmed both fail without the fix (an unhandled rejection and 2 calls instead of 1) via `git stash`. Full frontend suite: 98 pass, `tsc` clean.

### MEDIUM (frontend) — Deleting a document (or "start over") silently swallowed a failed backend delete

`removeDocument` and `resetWorkflow` (`KonverterContext.tsx`) removed the document from local state immediately (correct, for a responsive UI), then fired the backend DELETE with `.catch(() => undefined)` — a failure was completely invisible; the user would see the document gone with no error, while it was still present server-side, silently reappearing only if something later happened to call `refreshDocuments()`.

**Fix**: on a failed delete, both now show an error toast and re-sync from the server's own document list (`refreshDocuments()`) rather than leaving local and server state to drift — `resetWorkflow`'s bulk case uses `Promise.allSettled` to check all deletes and warn if any failed, instead of firing them completely fire-and-forget as before.
