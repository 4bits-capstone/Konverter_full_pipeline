## 5.2 Structural extraction performance

Two figures from an earlier development phase are worth reporting with their original context preserved, since they describe a model the team later moved away from rather than the system as shipped. An early evaluation of a fine-tuned LayoutLMv3 model, run against a 34-document annotated corpus, reported an F1 of approximately 0.94 (micro) and 0.93 (macro), with images and tables still identified as weak classes at that stage. A later evaluation cited in the project completion plan reported LayoutLMv3 at F1 of approximately 0.97. A separate development test also reported hierarchy resolution accuracy of 98.6 percent. Both of these later figures predate the team's decision, in week 8, to prioritise native Docling extraction over the custom layout model, on the grounds that it reduced dependency complexity while giving comparable or better results on the report structures actually in scope. They describe the performance of an approach that was tested thoroughly but ultimately not the one shipped, and should be read that way rather than as a claim about the final system.

The more direct evidence for the shipped system's structural performance comes from defects found and fixed against real client documents during later testing, each verified with an automated regression test and confirmed against the live document rather than a synthetic example. Four are summarised in Table 5-2.

| Defect | What went wrong | Verification |
|---|---|---|
| Diagram content flattened into one list | A sentencing-hierarchy diagram with four tiers, each with its own list of offences, was extracted as a single undifferentiated list under the last tier's heading only, misrepresenting the maximum penalty attached to each offence | Fixed and confirmed against the source document: each item now groups correctly under its own tier (2, 6, 9, and 8 items respectively, matching the source PDF exactly) |
| Page numbers misclassified as pictures | A page number rendered as part of a stylised chapter-opening design was classified as an embedded picture rather than recognised as text, across roughly 30 instances in the corpus checked | Fixed by independently re-reading the exact PDF region and confirming the recovered text is a genuine page number before excluding it; verified against five documents |
| Repeating chapter-divider graphics misclassified as content | A chapter-opening divider graphic, repeating once per chapter with the digit changing each time, was treated as a picture requiring review rather than decoration | Fixed using a position-clustering check confirmed by at least one instance carrying a structurally nested "Chapter N" label; verified against 11 occurrences in one report |
| Diagram-internal text leaking into body output | Labels belonging to a chart or diagram, such as axis values or a table legend split across several fragments, were extracted as independent floating paragraphs with no surrounding context | Fixed using a targeted classification check that only ever decides whether a fragment belongs to the diagram or is independent content, never altering the extracted text itself; confirmed against 20 real fragments on one report with no misclassifications found |

## 5.3 Review workload and audit trail

A sample report processed through the shipped pipeline produced 227 review flags, which the team identified as a meaningful workload for a single document and used as the basis for investigating footnote-specific confidence scoring. That investigation found that a low confidence score did not reliably predict an incorrect footnote, since many low-scoring footnotes were in fact correct. This led to a footnote auto-acceptance rule, verified by independently re-reading the source PDF's own text layer rather than trusting the confidence score alone, which reduced the review queue by roughly 60 percent on the example report used for testing.

A figure describing overall conversion and review time, roughly ten minutes against a previously reported four-hour manual workflow, was presented at the final client demonstration. This figure should be treated as a presentation claim rather than a controlled, repeatable benchmark, since it was not produced under timed, methodologically consistent conditions comparing the same document through both workflows. A proper timing evaluation is listed as outstanding work.

The audit trail itself met its stated target: every consequential action, upload, edit, approval, and publication, is recorded in an append-only, hash-chained log, verified insert-only at the database level. This gives a complete record of individual events. It does not currently provide a full document version history or a bulk-change view, which limits how efficiently a reviewer can work through a high-volume flag count like the 227 seen on the sample report; this is noted as a gap for future work rather than a shortfall against the stated M4 target, which was about traceability rather than review-interface efficiency.

## 5.4 Comparative evaluation against alternative pipelines

The team formally compared Marker 2 against the existing extraction pipeline on five selected reports. Marker 2 showed potential speed improvements, but format mismatches between its output and the team's schema, together with unresolved ground-truth consistency issues in the comparison itself, meant no confident migration decision could be reached. The final demonstration pipeline retained Docling, citing existing customisation and hosting constraints rather than a proven quality difference, and Marker 2 was kept as a future option rather than adopted.

A smaller, supplementary comparison was run later against Datalab's open-source Marker tool, using the same live client document and three specific structural cases already known to be meaningful: a table-shaped diagram, a flowchart-style infographic, and a two-column glossary. The result was mixed rather than a clean win for either tool. Marker handled the table-shaped diagram correctly without needing a fix, which the shipped pipeline only handled correctly after this cycle's structural fix described in Table 5-2. Marker flattened the flowchart into a static image with no extractable text at all, which is a more serious defect specifically for an accessibility product, since it means a screen-reader user receives nothing from that figure. The glossary was already correct in the shipped pipeline's base extraction, and this was not something fixed this cycle; Marker's output for the same glossary was severely scrambled. This comparison covered one document and three cases, and should be read as an illustrative data point rather than a representative benchmark; repeating it across a wider set of documents is listed as future work.

## 5.5 Known issues and considerations for future work

A small number of issues affect the current system and are discussed in full in Section 6. In summary: the backend's Docker build file is referenced in the deployment setup but is not currently present in the repository, which blocks rebuilding the backend image from source. The client's WordPress integration can only create new pages, not update existing ones, and while a safeguard warns before a likely duplicate publish, a reviewer can still choose to proceed. Every extraction rule in the pipeline was tuned against VLRC's own report format, and performance on a different document type or a different client's reports has not been established. Finally, one previously approved client document retains a duplicated heading in its appendix section even after a full re-extraction, because the underlying cause sits in logic shared by every document the system processes, and a safe fix would require full regression testing across the corpus rather than a quick patch.
